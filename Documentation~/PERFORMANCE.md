# Soft Additive 合成モデル と 最適化手法

大量のボリュメトリックビームを「白飛びさせず・影を保ちつつ・軽く」描くための中核技術。
全体構造は [ARCHITECTURE.md](ARCHITECTURE.md) を参照。

---

## 1. Soft Additive — なぜ「合計を見る」必要があるのか

### 問題

ボリュメトリックビームは物理的に**加算光**。素直に加算合成すると、N 本重なった領域の
輝度は N 倍に積み上がり、すぐ HDR で 1 を大きく超えて **真っ白** になる。すると:

- 中に立つ人物・キャラが光に飲まれて見えない
- ブルームが過剰な白を拾って画面全体が潰れる
- ACES 等のトーンマッパーが過剰輝度を **黄色〜オレンジへ色相シフト**させる

「実機のフォグはある濃さで飽和して薄く見える」という見た目を再現したい。

### 素朴な解が効かない理由

- **ブレンド係数の工夫(スクリーン合成 `dst + src(1−dst)`)**: 1 に漸近するだけで、
  天井は 1.0 = 白のまま。ブルームは依然として拾う。しかも HDR で `dst > 1` のとき
  係数が負になりビームが自己相殺して消える(実際に一度破綻した)。
- **フラグメント単位の Reinhard**: 各ビームを個別に K 未満へ抑えても、加算で合計は
  N×K に達する。1本の見た目は保てるが重なりは救えない。

**天井カーブは「重なった合計値」を入力に取らねばならない。** これはパスごと・
フラグメントごとの局所処理では原理的に不可能で、**一度オフスクリーンに合計を作る**
しかない。

### 実装(オフスクリーン蓄積 → 合計へ天井カーブ)

```
1. ビームを ARGBHalf オフスクリーン RT へ素の加算で蓄積(Blend One One)
2. 合成パスで合計値を  K·(1 − exp(−sum/K))  に通してシーンへ加算
```

`K` = ドライバの **Soft Max Brightness**(既定 0.5)。この曲線は:

- **原点で傾き1** → 1本の薄いビームの見た目は完全に不変
- **合計 → ∞ で K に漸近** → 何本重なっても絶対に K を超えない

`K=0.5` なら床のプールもフォグも「最大でも中間グレー」で頭打ちし、ブルームも
トーンマッパーも過剰入力を受け取らない。

## 2. 変調保存シーリング — 影とヘイズを潰さない

### 問題

天井カーブは合計が大きい領域で **微分がほぼ0**(`1−exp(−sum/K) ≈ 1`)。
ここへ「影による削れ」や「ヘイズの揺らぎ」といった相対変動を通すと、
どちらも一様な K に張り付いて **潰れて消える**。

### 解 — ベースラインを分離して比率を後掛けする

コーンシェーダは2系統を並走蓄積する:

| チャンネル | 中身 |
|---|---|
| RGB | 実際の寄与(**ヘイズ×影** 変調込み) |
| A | 純粋なビーム構造(`baseRaw / hazeF` = **ヘイズも影も除外**した無変調ベースライン) |

合成時:

```hlsl
float m       = clamp(lum(rgb) / alpha, 0.03, 4.0);   // = ヘイズ × 影 の合成変調率
float3 base   = rgb / m;                              // 無変調ベースラインを復元
outRGB        = K·(1 − exp(−base/K)) · m;             // ベースラインを飽和 → 変調を後掛け
```

天井は**無変調ベースラインだけ**に掛かるので飽和で潰れるのはベースラインのみ。
影の削れ・ヘイズの流れは比率 `m` として最後に掛け戻され、**重なり深さに関わらず残る**。
下限クランプ 0.03 は深い影をちゃんと暗く出すため(旧 0.25 では最大4倍コントラストに
制限され影が浅かった)。

> **物理的限界**: 多灯が密集すると、ある灯体の影の位置を他の灯体が普通に照らす。
> 比率 `m` は重なった全ビームの平均なので、1灯だけ影でも残りで薄まり `m≈1` になる。
> これは実機の舞台でも起きる「多灯で陰影が洗い流される」現象で、変調保存では救えない
> (救うには非物理的な「重なり本数での正規化」が要る)。演出的には影を見せたい灯体を
> 集める/他を絞るのがコンソール的な対処。

### デカールも同じ器で

床の投影プール(デカール)も同一問題を持つ。専用の ARGBHalf バッファへ素の加算で
蓄積し、α にプール自身の輝度を書く(→ 合成の変調率 `m≈1`)。同じアップサンプル+
天井シェーダで合計を K に飽和させてから合成する。これで**プールもビームと同じ K で
頭打ち**し、多数重なっても白飛び・ブルーム潰れ・ACES 変色が起きない。

## 3. 最適化手法カタログ

### 3.1 共有占有ボリューム(灯数非依存の核心)

シャドウデータを **1つの世界空間3Dテクスチャに集約**し、各ビームはそれを*参照する
だけ*。占有ボリュームの構築コストは灯体数と無関係(遮蔽物の数だけに依存)なので、
**灯体を増やしてもシャドウコストは一定**。per-light シャドウマップが N 枚/フレームで
破綻するのに対し、これが「200灯を影付きで」を可能にする唯一のアーキテクチャ。

### 3.2 シャドウ項の間引き

シャドウ項は視線に沿ってビーム減衰よりずっと**緩やかに変化**する。そこで
**偶数ステップだけ再サンプルし、奇数ステップは前回値を再利用**(`shadowCache`)。
支配的コストだった「レイマーチ×3Dテクスチャタップ」が半減し、見た目の差はない。

### 3.3 ズーム適応レイマーチ

ワイドズームのビームは画面被覆が (角度比)² で増える一方、光束保存で**単位体積あたり
暗く柔らかい**ためサンプル数を減らしても破綻しない。20°基準で角度に反比例、40°で×0.5
(下限8)。「ズーム拡大でピクセル数×ステップ数が両方増える」二重苦の片方を打ち消す。

### 3.4 ワールド固定ボクセル格子(アンチシマー)

AutoFit の箱が被写体追従で毎フレーム微動すると、ボクセル格子がワールドに対して
サブボクセル移動し、**全ボクセルが再量子化されてチラつく**。対策として箱サイズを
1m刻みに量子化(ボクセルサイズを区分的に一定化)+最小コーナーをボクセル整数位置へ
スナップ。被写体は「静止した格子の中を動く」形になりシマーが原理的に消える。

### 3.5 ズーム光束保存

実機はズームを広げると同じ光束が広い立体角に薄まって暗くなる。強度を
**Ω(基準角) / Ω(実角)**(Ω = 2π(1−cos θ/2))でスケールし、これを再現。
「ワイドの中に立つと真っ白で見えない」を防ぐ物理的な副作用も得られる。
基準は GDTF ネイティブ FieldAngle(定格角度で ×1)。

### 3.6 メッシュボクセル化(品質と灯数非依存の両立)

球/カプセル近似を捨て、遮蔽物の**実メッシュを3軸から直交ラスタライズ**して
ボクセルへ UAV 書き込み。スキニング・布変形込みの実シルエット影が、灯数非依存の
まま得られる。ボクセル化は三角形=**表面殻しか書かない**ので、後段の compute で:

1. **GrowMax(純 max)×2** で空洞の内部を 1.0 で充填(中間値を作らない)。
2. **Blur ×2** で硬い縁を連続グラデ化。max 膨張は 1.0→0.7→0.49 の離散殻を作り
   シャドウ積分が**縞状(terracing)**になるため、充填後に blur するのが鍵。
3. **TemporalBlend(時間 EMA)** でワールド固定格子の履歴と混ぜ、動く遮蔽物の
   ボクセル間ポッピングを吸収して影の縁を滑らかに滑らせる。

### 3.7 描画領域の削減(カリング・解像度・更新間隔)

このライトの負荷は重なりに加え**画面被覆**が支配的。3つのオプションで領域を削る:

- **ビーム境界球カリング**: 視錐台外・画面投影半径が `_minScreenRadiusPx` 未満の
  ビームをキュー段階で棄却。遠く/画面外/極小のビームにフラグメントを割かない。
- **解像度スケール(Full/Half/Quarter、既定 Quarter)**: レイマーチ RT を縮小
  (Quarter でピクセル 1/16)。合成は**深度考慮アップサンプル**(joint bilateral)で縁の
  破綻を防ぐ。見た目(ビーム縁の鮮鋭さ)と負荷の主要トレードオフレバー。低いほど安く、
  高いほど鮮鋭。既定 Quarter はバランス点。ヘイズ流速一致ジッターで低解像度時のグレインは
  和らぐ(TAA の要否は好み次第)。
- **VolumeUpdateInterval**: 占有ボリュームを N フレームおきに再構築(構築コスト 1/N)。

### 3.8 その他の実装規律

- **プール済み MPB**:ビーム1本あたりマテリアル複製ゼロ・GC ゼロ
- **`Shader.PropertyToID` の static キャッシュ**:毎フレームの文字列ハッシュを排除
- **`ref readonly` で大きな struct を参照読み**:`ChannelOp` 等のコピー回避
- **キーワードでシャドウ off をコンパイル除去**:未使用パスは命令自体が乗らない

### 3.9 GPU インスタンシング(灯数が多く CPU がボトルネックのときだけ効く)

ビーム1本ごとの `DrawMesh` を、**ゴボ配列ペアごとに1回の `DrawMeshInstancedProcedural`** に
束ねるオプション(`StageBeamDriver ▸ Gpu Instancing`、既定 OFF)。per-beam パラメータは
`StructuredBuffer<GpuBeam>` に積み、シェーダが `SV_InstanceID` で引く。同一フィクスチャ型は
ゴボ配列を共有できるので、スライス番号をインスタンス単位で変えて1バッチに収まる。

**大事な前提**:インスタンシングが減らすのは**ドローコール(CPU)だけ**で、フラグメント
(フィルレート)負荷は減らない。このライトは基本フィルレートがボトルネックなので、素朴に実装すると
むしろ**遅くなる**——その理由と対策が学びどころ:

- **素朴版が負けた理由**:uniform パスは per-beam 値を **cbuffer(定数レジスタ)**から読む=
  ほぼ無料。素朴なインスタンス版は per-beam 値を **StructuredBuffer からフラグメントごとに
  読む**(1灯 240 バイト)。フィルレートがボトルネックのシェーダでは、この per-pixel バッファ読みが
  ピクセルコストを押し上げ、ドローコール削減の得を食い潰す。
- **対策(varying 化)**:GpuBeam を**頂点シェーダで1回だけ読み**、パラメータとオブジェクト
  空間座標を **flat 補間 varying** でフラグメントへ渡す(`worldToObject` も frag から消える)。
  これで per-fragment のバッファ読みがゼロになり、per-pixel コストは cbuffer 版とほぼ同等。
  結果、120灯で**誤差レベルの微勝ち**(ドローコール削減分)まで持ち直した。

**要点**:フィルレートがボトルネックの演出では気休め程度。効くのは「小さい灯を大量に=ドローコール/CPU
がボトルネック」の極端なケース。**既定 OFF 推奨**、灯数が非常に多く CPU がボトルネックだと感じるときだけ ON。
制約:Volume/Screen/影なし専用(LightShadowMap は per-beam ライトインデックスをグローバルで
渡せないため非対応)。

RTX 5060 Ti / FullHD:

| シーン | FPS | GPU frametime |

| UnityChanKagura 1体 + 単灯 | (余裕) | — |
